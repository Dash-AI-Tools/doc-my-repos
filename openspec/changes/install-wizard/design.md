# Design

## Context

See `proposal.md` for the motivation and the three specs (`install-wizard`, `github-app-provisioning`, `release-artifacts`) for behaviour. Current state that shapes the approach:

- The recommended install is clone, `cp .env.example .env`, edit, `docker compose up -d --build --wait`. The compose file `build`s from the repository `Dockerfile` (`image: docmyrepos:local`); **no image is published anywhere**, so an installer outside a checkout has nothing to pull.
- Required settings are validated by `src/server/config/env.ts`: `DATABASE_URL`, `GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID` (positive integers), exactly one of `GITHUB_APP_PRIVATE_KEY` (inline, `\n` escapes accepted) or `GITHUB_APP_PRIVATE_KEY_PATH` (an unencrypted RSA PEM), and `GITHUB_WEBHOOK_SECRET`, `SYNC_SECRET`, `SESSION_SECRET` (at least 16 characters, the `replace-with-` placeholders are rejected). `ADMIN_EMAIL` / `ADMIN_PASSWORD` (12+ characters) create the first admin on first login while `users` is empty. `docmyrepos.config.yml` only narrows repositories (`repos` or `exclude`, bare names).
- The compose file carries the hardening (read-only root, `tmpfs /tmp`, dropped capabilities, `no-new-privileges`, pids limit, log rotation, loopback binds, `init: true`, health check from the image on `/api/health`). The container user is uid 1000, which matters for a mounted key file.
- `docs/github-app-setup.md` documents manual registration (5a, tested by hand once) and a manifest flow (5b, **never run**: it lists unverified points, such as whether `installation` events need to be in `default_events`, and whether GitHub requires further manifest fields). The manifest at `docs/github-app-manifest.json` has a placeholder host.
- `POST /api/sync` with `Authorization: Bearer <SYNC_SECRET>` starts a sync; the scheduler (on in the image) also starts one ~10 seconds after boot and hourly, so webhooks are an optimization and not required for correctness.
- CI (`.github/workflows/ci.yml`) pins actions to SHAs, runs read-only, and has a Docker smoke test (`scripts/docker-smoke.sh`). The repository is a single pnpm project (`pnpm-workspace.yaml` holds only build-script settings); the tsconfig include list and ESLint config cover `src`, `e2e` and `scripts`.
- `CLAUDE.md`: secrets only from environment variables, never in logs; GitHub access is always a GitHub App, never a personal token; the App is read-only.

## Goals / Non-Goals

**Goals:**
- From nothing to a signed-in, syncing portal with one command and answers a person can give in a few minutes.
- A tool that is safe to run by people who will not read its source: no surprise network calls, no secrets in output or arguments, no overwriting.
- Fewest moving parts to trust: zero runtime dependencies, one published image, one published package.

**Non-Goals:**
- TLS termination, reverse proxy, DNS, or cloud/Kubernetes installs; upgrades, uninstall, backups; a GUI; installing from source.
- Creating the organization's GitHub App as anything but read-only, or with a personal access token.

## Decisions

**1. A `create-*` package, zero dependencies, plain Node.** `npm create docmyrepos` and `npx create-docmyrepos` are the established convention for "set me up" tools and need no global install. The wizard uses only Node built-ins (`node:readline/promises`, `node:crypto`, `node:http`, `node:fs`, `node:child_process`, global `fetch`), so there is nothing in its dependency tree to audit or to be compromised, and the package stays small. It lives in `packages/create-docmyrepos/` as a workspace package, written in TypeScript (strict, like the app), compiled with `tsc` to ESM in `dist/`, with a `bin` entry. It imports nothing from `src/`: the checks it needs (secret length, URL and email shapes, PEM check) are re-implemented small and covered by tests that compare them with the app's `env.ts` on a shared fixture list, so the two cannot drift silently. Alternatives: `@clack/prompts` (nicer prompts, but a dependency tree on an installer); a shell script (no Windows, hard to test); a hosted web installer (sends secrets to a third party).

**2. Structure: pure steps behind small interfaces.** `plan` (answers → file contents, pure and snapshot-tested), `prompts` (the only code that touches the terminal, taking an injectable `io` for tests), `github` (manifest flow, JWT, installation and repository calls, taking an injectable `fetch` and base URL for the fake server), `docker` (preflight and compose commands through an injectable runner that uses `spawn` with an argument array and `shell: false`), `files` (atomic, mode-aware writes), and `run` (the orchestrator, which is the only place that sequences them). `--dry-run` is the orchestrator skipping the effectful steps, so the plan printed is the plan executed.

**3. Prerequisite checks before any effort.** `docker --version`, `docker compose version` (v2 only, with the minimum version `--wait` needs), `docker info` (daemon reachable), the target folder (exists-and-empty or creatable; an `.env` or compose file already there stops the run), and the port (try binding it on loopback). Order is cheapest first and all run before the first prompt that matters.

**4. GitHub App through the manifest flow, with a local callback.** The wizard builds the manifest from `docs/github-app-manifest.json` (the single source, loaded into the package at build time and checked by a test against the permission list in the setup guide): `default_permissions` `contents: read`, `metadata: read`; `default_events` `push`, `repository` (the guide's open question on `installation*` events stays open and is settled by the spike); `public: false`; `url` the portal address; `hook_attributes` with the real webhook URL and `active: true` only for a public `https` address, otherwise `active: false`; `redirect_url` `http://127.0.0.1:<port>/callback`. GitHub's flow needs a POST of the manifest from the browser, so the wizard serves a one-time local page (`http://127.0.0.1:<port>/start?...`) with an auto-submitting form to `https://github.com/organizations/<org>/settings/apps/new?state=<state>`; it opens that page in the browser (`open` / `xdg-open` / `start` via `spawn`, never a shell) and prints it as a fallback. The callback handler: loopback bind on port 0, accepts only `GET /callback` with the exact `state` (256-bit random, constant-time comparison), handles it once, answers a static "return to the terminal" page, closes the server, times out after 10 minutes. The code is exchanged with `POST https://api.github.com/app-manifests/<code>/conversions` (no auth, valid for one hour) giving `id`, `slug`, `pem` and `webhook_secret`, kept in memory only. The webhook secret from GitHub is used when it is at least 16 characters (the app's minimum), else the wizard sets one. Alternative: asking the user to copy the code from the address bar (the existing guide) is kept only as the fallback route.

**5. Installation discovery instead of a setup URL.** After creation the wizard opens `https://github.com/apps/<slug>/installations/new`, then polls `GET /app/installations` (a short-lived App JWT, `RS256`, built with `node:crypto`, 9 minute expiry, `iat` backdated 60 seconds) every 3 seconds until an installation whose `account.login` equals the chosen organization (case-insensitive) appears or 10 minutes pass. This avoids a `setup_url` callback (one more redirect to get right, and its manifest support is unverified) and also serves the "existing App" route. An installation on a different account is reported by name. Repositories are then listed with an installation token (`POST /app/installations/<id>/access_tokens`, then `GET /installation/repositories`, paginated, capped at 1,000 names for the picker), used in memory and never written.

**6. Existing App route validates against GitHub.** Id, key file path, webhook secret. The key goes through the same PEM rules as the app (unencrypted RSA, PKCS#1 or PKCS#8). The wizard calls `GET /app` with a JWT: success proves id and key match and gives the App's name and `permissions`, and any permission other than `contents: read` and `metadata: read` (any `write`, or others) raises a warning that requires a confirmation. Errors are mapped to fixed messages; the response body is shown only if it passes a credential-pattern check (it never should contain one).

**7. Files and where the key lives.** Written with `fs.writeFile` to a temporary name in the same directory with mode `0600` then `rename` (atomic on one filesystem), the directory `0700`. `.env` has every required variable, `DATABASE_URL` for the in-compose database is not needed (compose composes it from `POSTGRES_*`), the database password is generated and goes into `.env` as `POSTGRES_PASSWORD`, and `ADMIN_EMAIL` / `ADMIN_PASSWORD`. The private key: the app prefers a file and the container runs as uid 1000, so a `0600` file owned by someone else is unreadable inside. The wizard writes `github-app.private-key.pem` and mounts it as a compose file secret when the host user is uid 1000 or the OS is macOS/Windows (Docker Desktop maps ownership), and otherwise puts the key inline in the `0600` `.env` (`GITHUB_APP_PRIVATE_KEY` with `\n` escapes) and says why. The spike/CI test proves both layouts start. `.gitignore` is written next to them ignoring `.env`, `*.pem` and backups, in case the user commits the folder.

**8. The compose file is a template, checked against the repository's.** The package carries `compose.template.yml` built from the repository's `docker-compose.yml` with `build:` replaced by `image: ghcr.io/dash-ai-tools/doc-my-repos:${DOCMYREPOS_VERSION}` (substituted with the installer's own version at write time and also left as a variable default so `docker compose pull` of a later version is a one-line edit). A unit test parses both and asserts the hardening keys are equal (`read_only`, `tmpfs`, `cap_drop`, `security_opt`, `pids_limit`, `logging`, `init`, loopback `ports`, `healthcheck`, the volumes of the config file), so changes to the repository file that matter are never missing from the installer. The database port is **not** published in the generated file (the dev-only exposure in the repository file is for the host app), and the database password is never the default.

**9. Start-up and verification.** `docker compose pull`, `docker compose up -d --wait --wait-timeout 180` (falling back to polling `http://127.0.0.1:<port>/api/health` for `200` when `--wait` is unavailable), then `POST /api/sync` with `Authorization: Bearer` from a child-process environment, not an argument (the wizard calls it with `fetch`, from the host, to the loopback port). On failure it prints the failing step, the last 30 lines of `docker compose logs app` (the app never logs secrets) and the command for more. The final summary shows the address, the admin email, how to follow the sync (`/status`), and the bootstrap cleanup offer: if the user confirms they have signed in, the two lines are removed from `.env` atomically and `docker compose up -d` recreates the app.

**10. Non-interactive mode.** Every question has a flag (`--org`, `--url`, `--port`, `--admin-email`, `--dir`, `--repos all|a,b,c`, `--app existing|create`, `--image-tag`), and secrets come only from environment variables or files (`DOCMYREPOS_ADMIN_PASSWORD`, `DOCMYREPOS_APP_KEY_FILE`, `DOCMYREPOS_APP_ID`, `DOCMYREPOS_INSTALLATION_ID`, `DOCMYREPOS_WEBHOOK_SECRET`), so nothing secret lands in shell history or `ps`. `--yes` with a non-TTY stdin and a missing answer lists every missing answer at once and exits 2. The manifest route needs a browser and is refused in non-interactive mode unless an existing App is given (CI uses the fake GitHub through `DOCMYREPOS_GITHUB_API_URL`, a documented test-only override that is rejected unless the host is loopback).

**11. Release pipeline.** `.github/workflows/release.yml` triggers on `v*.*.*` tags only, `permissions` minimal per job. Jobs: `verify` (the full CI set plus the installer end-to-end test against the image built in this run), `image` (QEMU and Buildx, build `linux/amd64,linux/arm64`, push `ghcr.io/dash-ai-tools/doc-my-repos:<version>` with `GITHUB_TOKEN` `packages: write`, provenance and SBOM attestations; a guard fails if the tag already exists in the registry), `npm` (`pnpm --filter create-docmyrepos build`, check that the package version equals the tag, `npm publish --provenance --access public` with `id-token: write`, using npm trusted publishing (OIDC) if configured, else a scoped automation token stored as an environment secret limited to the release environment). A `release` environment with required reviewers gates the publishing jobs. `if: github.repository == 'Dash-AI-Tools/doc-my-repos'` keeps forks from publishing. Versioning: the root `package.json` version, the package version and the tag are checked equal by a script run in `verify`. Alternative: Changesets or release-please (more machinery than a two-artifact lockstep release needs; revisit if releases become frequent).

**12. The image gets labels and nothing else changes.** `org.opencontainers.image.source`, `.version`, `.licenses` and `.revision` are added by the build step (`docker/metadata-action`-style labels or `--label`), not baked into the Dockerfile text, so the Dockerfile stays reproducible. No runtime change.

## Risks / Trade-offs

- [The manifest flow has never run against GitHub] → A spike task (a human, on a throwaway organization, 30 minutes) runs it before the rest is built and records the answers to the guide's open questions (event list, required manifest fields, `http://127.0.0.1` redirect acceptance). The fallback is the guided manual route, which the design keeps anyway.
- [The loopback callback is a local web server] → Random port, loopback only, single-use, `state` check, 10 minute lifetime, static page with no secrets; the secrets arrive through an outbound HTTPS call the wizard makes itself, not through the browser.
- [A published installer is a supply-chain target] → Zero runtime dependencies, provenance, OIDC, a gated release environment, a pack-contents test, and a README telling people how to read the source before running (`npm view`, `npm pack`). 2FA on the npm account/org is required for publish.
- [Installer and app drift] → The compose and validation shapes are tested against the app's, versions are locked together, and the end-to-end install test runs in CI on every pull request that touches the package, the compose file, `env.ts` or the Dockerfile.
- [Private key permission on Linux] → The uid logic in decision 7 plus tests for both layouts; the inline fallback is documented with its trade-off (visible in `docker inspect` to root-equivalent users).
- [The admin password sits in `.env` until cleanup] → Owner-only file, the cleanup offer at the end, a printed reminder; the app already documents removal.
- [Windows quirks] → Paths via `node:path`, no shell, `docker.exe` resolution by `spawn`, file modes best effort there (documented); CI runs the unit tests on Windows and the install test on Linux.
- [GHCR package visibility] → The first publish makes a private package; a one-time manual step sets it public, written in the release checklist task.

## Migration Plan

Additive. Nothing changes for existing installs, which keep working and can adopt the published image by changing `build: .` to the `image:` line. Releasing the first version requires the one-time setup in the release checklist (npm name reserved and 2FA, GHCR package made public, the `release` environment created). Rollback of a bad release: deprecate the npm version (`npm deprecate`) and publish a patch; image tags are never moved.

## Open Questions

- Whether to offer a Caddy-based TLS option later for public installs. It would be a new optional step and does not change these specs or the task breakdown.
