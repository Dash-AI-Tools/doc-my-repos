## Context

See `proposal.md` for the motivation and `specs/org-branding/spec.md` for behaviour. Current state that shapes the approach:

- Colors are semantic CSS variables on `:root` and `.dark` in `src/app/globals.css`, mirrored in `src/lib/theme-tokens.ts` (a unit test fails if they drift) with a `CONTRAST_PAIRS` table and a `contrastRatio` helper. Light and dark are tuned separately (light primary `#2b59ff`, dark `#7c9bff`).
- `primary`, `ring`, `link`, `link-hover`, `accent`, `accent-foreground`, `selection` and the OKF badge pair are the brand-bearing tokens. Mermaid and Shiki use neutrals, so they are unaffected.
- The CSP is `style-src 'self' 'unsafe-inline'` (with a comment that a nonce must NOT be added there) and `img-src 'self' https:`. Same-origin images are fine; inline `<style>` is fine.
- `SiteHeader` hard-codes the "DocMyRepos" wordmark and uses `bg-background`, `text-foreground`, `text-muted-foreground`. `SiteFooter` is a text line plus a Sync status link. The root layout is already dynamic (`getCurrentUser()`, nonce) and sets `metadata.title: "DocMyRepos"`; several pages hard-code `· DocMyRepos` in their titles and four e2e specs assert them.
- `src/proxy.ts` gates everything except `isPublicPath`. The login page renders inside the same layout, so it shows the header too.
- `src/server/assets/image-types.ts` already detects image types from bytes (including SVG) and `serve.ts` already serves untrusted images with `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` (SVG adds `style-src 'unsafe-inline'`) and `Cross-Origin-Resource-Policy`.
- Two other changes also touch the header: `starred-repos` (an account menu replaces the Admin link and Sign out) and `responsive-docs-reader-layout` (publishes `--site-header-h`). This change must apply on top of whichever lands first and must keep the header's measured height working.

## Goals / Non-Goals

**Goals:**
- Branding that cannot make the portal inaccessible or unsafe: any valid color yields AA-readable output, and no branding value can inject markup, style or script.
- Zero change for portals with no branding set.

**Non-Goals:**
- Separate light-theme and dark-theme logo files (inversion is the answer here), favicon or social-image branding, fonts, per-user themes, multiple brands, or a config-file way to set branding (admin page only, like allow/block and users).
- Letting admins hide the DocMyRepos credit.
- A color picker beyond the browser's native color input plus a hex field.

## Decisions

**1. One `site_branding` row, not config-file keys.** Columns: `id smallint primary key check (id = 1)`, `org_name text`, `page_title text`, `primary_color text`, `accent_color text`, `colored_header boolean not null default false`, `invert_logo_on_dark boolean not null default true`, `logo bytes bytea`, `logo_type text`, `logo_version integer not null default 0`, `updated_at`. Null means default. Admin-editable runtime settings already live in Postgres (`users`, `repos.is_allowed`); `docmyrepos.config.yml` is deployment configuration read at boot, and "orgs should be able to update" implies no redeploy. The logo is stored in the row (at most 512 KB): the app already depends on Postgres, there is no object store, and one small blob avoids a volume to mount and back up. Alternative: a file on disk (breaks stateless containers). The row is read per request through `cache()` (one primary-key read); no cross-instance cache invalidation to get wrong.

**2. Pure derivation library, `src/lib/branding/`.** No React, no server imports, so the admin preview (client) and the layout (server) run the same code. `deriveBrandTokens({ primary, accent }) → { light, dark }` returns only the tokens it overrides:
- Foreground on a fill is `#ffffff` or `#000000`, whichever contrasts more. The better of the two is always at least 4.58:1 for any color, so the primary can be used unchanged as a fill and button text is always readable.
- Text and focus colors (`link`, `link-hover`, `ring`) are the primary shifted in HSL lightness (hue and saturation kept) until they meet 4.5:1 (links) or 3:1 (ring) against the background, muted, card, popover and code surfaces of that theme. In light that darkens pale colors; in dark it lightens deep ones. If the shift hits white or black it stops there, which still passes.
- Dark `primary` (the fill in dark) is the lightened variant, so it doubles as readable text there, matching how the shipped dark palette works.
- Dark surfaces follow the primary: when one is set, the dark `background`, `card`, `muted`, `popover`, `secondary`, `code-background` and `border` are the primary's hue and saturation at fixed dark lightness steps (16–32%), so a branded dark theme reads as a dark shade of the brand rather than near-black; `foreground`, `muted-foreground`, `code-foreground` and `input` are re-derived with `shiftToMeet` against those surfaces, so AA holds for any hue. Nothing is emitted when no primary is set, so the neutral dark palette stands.
- Accent: the chosen color is the light-theme tint with `accent-foreground` derived to 4.5:1 on it (a dark shade of its hue, else black/white); in dark, a deep shade of the hue mixed toward the dark surface with a light foreground. The OKF badge pair follows accent, as it does in the shipped palette.
- `selection` and `selection-foreground` follow the primary.
A property-style unit test sweeps hues, saturations and lightness extremes (black, white, greys, yellows, pure primaries) and asserts every pair in a branding-specific copy of `CONTRAST_PAIRS`, using the existing `contrastRatio`, so the guarantee is tested rather than argued.

**3. Applying colors: a validated inline `<style>`.** The root layout renders `<style id="branding">html:root{--primary:#…;…} html.dark{…}</style>` in `<head>` when any color is set, and nothing otherwise. The `html:root` / `html.dark` selectors beat `:root` / `.dark` in `globals.css` regardless of stylesheet order. Every value is a `#rrggbb` produced by derivation from a re-validated input (decision 7), so no stored string reaches the CSS verbatim. `style-src 'unsafe-inline'` already allows it, and no nonce is added there (existing constraint). `theme-tokens.ts` stays the source for defaults; the override layer only exists when branding is set, so the default render is byte-for-byte what it is today. No flash: it is in the server HTML. Alternative: a runtime `<link>` to a generated stylesheet (an extra request, cache invalidation).

**4. Colored top bar through header tokens.** New tokens `header`, `header-foreground`, `header-border`, `header-ring`, defaulting to `background`, `foreground`, `border`, `ring` in `globals.css` (and mirrored in `theme-tokens.ts` with contrast pairs, so the drift test covers them). The header, the wordmark/logo link, the nav, the search trigger, the theme toggle and the account controls switch from `text-foreground`/`text-muted-foreground` to the header tokens. Muted text on a colored bar would need its own contrast-checked shade, so when the bar is colored the header's secondary text uses `header-foreground` with weight and underline, not a dimmer color. When `colored_header` is on, the override block sets `--header` to the primary and `--header-foreground` to its readable foreground; in dark it sets `--header` to a deep shade of the primary with a light foreground (a full-strength light-blue bar on a near-black page is glaring) and `--header-ring` to `--header-foreground`. When it is off and a primary is set, the dark block sets the bare header tokens to the derived dark page surface, text and border, so the bar follows the tinted page instead of staying the neutral near-black of `globals.css`. The popovers (command palette, account menu) keep the popover tokens, so only the bar itself changes.

**5. Logo storage and serving.** Upload: `PUT /api/admin/branding/logo`, raw body, `Content-Length` required and checked against 512 KB, and the stream is read with a hard cap so a lying header cannot exceed it. The type is detected from the bytes with the existing `image-types.ts` (restricted to png, jpeg, webp and svg; the declared Content-Type and file name are ignored). Serving: `GET /api/branding/logo`, public (added to `isPublicPath`, with a proxy test), 404 when none; headers mirror the asset proxy: `Content-Type` from the verified type, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` (SVG adds `style-src 'unsafe-inline'`), `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer`, and a strong `ETag`. The page references it as `/api/branding/logo?v=<logo_version>` with `Cache-Control: public, max-age=31536000, immutable`; the version bumps on every upload or removal, so replacements are never stale. An `<img>` never runs SVG script, and the sandbox CSP covers direct navigation. The logo is public to anyone who can reach the app because the sign-in page shows it; it is not secret. Alternatives: raster only (rejects the most common logo format); sanitizing SVG (a parser to maintain; sandboxing is simpler and safer).

**6. Header, title and footer.** The header shows one link to `/`. With a logo it shows `[logo] [page title]` (the organization name would read as a duplicate of the logo); without one it shows `[org name] · [page title]`, each only when set, else the existing wordmark. The logo's `alt` is empty when the title is visible beside it, so assistive technology does not read it twice, and is "Home" when the logo stands alone. The logo is a fixed-height box (`h-8`, `max-w-40`, `object-contain`) so the header height, which the document page measures, never depends on the image. A small horizontal shift on a first uncached load is accepted. The root layout's `generateMetadata` sets `title: { default: pageTitle, template: "%s · " + pageTitle }`; pages that hard-code `· DocMyRepos` return just their own part, the global error page (which cannot read the database) keeps "DocMyRepos". Footer: "Powered by DocMyRepos" and a small "★ Star" link, both to `https://github.com/Dash-AI-Tools/doc-my-repos` from one constant in `src/lib/site.ts`, `target="_blank" rel="noopener noreferrer"`, the star as an inline SVG so there is no external image, counter or badge request; the Sync status link stays. Nothing in the branding data model can address them.

**6a. Logo inversion by CSS variable.** The logo `<img>` has `filter: var(--logo-filter, none)`. The override block sets `--logo-filter: invert(1)` in exactly the surfaces that are dark: `html.dark` always (dark theme, whether or not the bar is colored, because the dark bar is a deep shade with light text), and `html:root` only when the bar is colored and its derived foreground is `#ffffff` (a light-theme bar filled with a dark primary). Whether to emit these rules is decided by `invert_logo_on_dark` and by the derived header foreground, both known when the block is built, so the rule lives in the same pure `brandStyleBlock` as the colors and is unit tested. The block is rendered when colors are set or when a logo exists with inversion on; with no logo and no colors, nothing is emitted and the page is unchanged. The filter keeps alpha, so transparent logos invert cleanly. It assumes a logo drawn dark-on-transparent for light pages, the common case; the switch exists for full-color or already-light logos. `filter` has no effect on layout, so the fixed-height logo box and measured header height are unaffected. The admin preview applies the same variable inside its light and dark panels, so it is accurate by construction. Alternatives: a second uploaded logo (extra storage, API and form fields, and the user asked for CSS); `mix-blend-mode` tricks (fragile on colored bars); inverting the stored bytes (alters the original and needs an image pipeline).

**7. Validation, twice.** `src/lib/branding/validate.ts`: names trimmed, 1 to 60 chars; titles 1 to 70; no control or bidi-override characters; colors lower-cased and exactly `^#[0-9a-f]{6}$`. Used by the admin handlers on write (400 with a field-named message) and again in `getBranding` on read, where an invalid stored value becomes null (the default) instead of throwing, so a bad row can never take the site down or reach the style block. Text is only ever rendered as React text nodes and in `<title>` through Next's metadata.

**8. API and admin page.** `GET /api/admin/branding` (current settings, logo version, no bytes), `PUT /api/admin/branding` (the five settings; a null or empty value clears that field; all fields validated before any write), `PUT`/`DELETE /api/admin/branding/logo`, `DELETE /api/admin/branding` (reset everything). All behind `requireAdmin` in `src/server/admin/service.ts`, thin route files like the rest. `/admin/branding` is a server page rendering a client `BrandingForm`: text fields, `<input type="color">` paired with a hex field for each color (the same value, validated as typed), a checkbox for the colored bar, the logo upload with a preview and a Remove button, Save and Reset. A preview panel runs the derivation client-side and shows the top bar plus sample button, link and badge in light and dark side by side, including the derived link color when it differs from the chosen one. Saved with one `PUT`; on success `router.refresh()`. The page is linked from the admin overview and from the account menu if the `starred-repos` change has landed (whichever is applied second adds the link).

## Risks / Trade-offs

- [Auto-darkened link colors differ from the exact brand color] → Accepted: readability is not negotiable; the fill uses the exact color, and the preview shows the derived shade so admins are not surprised.
- [CSS inversion suits dark-on-transparent logos; a full-color logo gets odd colors and a JPEG with an opaque white background becomes a black rectangle] → The switch turns it off per portal, the preview shows exactly what visitors will see in both themes and on the colored bar, and the README recommends a transparent PNG or SVG. Hue-preserving tricks (`hue-rotate`) are not used because they distort brand colors unpredictably.
- [SVG logos can carry script] → Never inlined, only served as an image under a sandbox CSP with `nosniff`; tests include a script-bearing SVG opened directly.
- [Public logo route exposes the logo to anyone who can reach the app] → Intentional (sign-in page); it is branding, not data. Documented.
- [A per-request database read for branding] → One primary-key read, deduplicated per request by `cache()`. The home page already queries; accepted.
- [Both the header and footer text change for every page, and four e2e specs assert old titles] → Defaults keep the old titles, so those specs pass unchanged; new e2e covers the branded titles.
- [Concurrent changes to `site-header.tsx` by `starred-repos` and `responsive-docs-reader-layout`] → Tasks re-read the file before editing, keep the measured header height working (checked by the existing header-height tests), and the account-menu link is added by whichever change lands second.
- [Large logos stored as `bytea` bloat row reads] → The logo column is excluded from `getBranding`'s normal select; only the logo route and the upload read or write it.
- [Admins who modify the source can remove the credit] → Out of scope; the product does not offer a switch, which is the commitment made here.

## Migration Plan

1. `pnpm db:generate` emits `CREATE TABLE "site_branding"`; `pnpm db:migrate` applies it. No row is created: absence means defaults.
2. Deploy. Nothing changes visually until an admin saves branding, apart from the footer credit.
3. Rollback: deploy the previous build, which ignores the table; dropping it is optional.

## Open Questions

None that change the specs or approach. Assumptions recorded: branding is edited in the admin UI and stored in Postgres; "page title" is the tab-title suffix and defaults to the organization name; "accent" is the tint color used for badges and highlights; the colored bar uses the primary color; one logo file serves both themes, with CSS inversion on dark surfaces (on by default, switchable); the credit target is the `Dash-AI-Tools/doc-my-repos` repository named in the README.
